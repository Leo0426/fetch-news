## 一手资料提供的依据

1. **条件请求能避免重复传输未变化的正文。** HTTP 规范定义了 `ETag` / `If-None-Match`、`Last-Modified` / `If-Modified-Since`；`304` 表示可以更新并复用相应已存响应。项目应把“未变化”视为成功检查，不能解析空正文或清空已有条目。这是规范事实；先从通用 RSS 路由落地是本项目的范围选择。[RFC 9110 §13.1.2–13.1.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.2)、[RFC 9111 §4.3.3–4.3.4](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.3.3)
2. **刷新频率、失败退避和并发数是不同控制量。** `Retry-After` 可表达秒数或 HTTP 日期；429 表示限流。Miniflux 官方实现配置也分别提供每主机并发限制、按历史更新频率调度和刷新间隔边界。规范支持等待，产品配置证明这种拆分已有实践；不能据此推断 fetch-news 会获得某个固定比例的性能提升。[RFC 9110 §10.2.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.3)、[RFC 6585 §4](https://www.rfc-editor.org/rfc/rfc6585.html#section-4)、[Miniflux 配置](https://miniflux.app/docs/configuration.html)
3. **FTS5 已有能力需要针对中文验证。** 默认 `unicode61` 将连续 token 字符作为一词，未承诺中文分词；`trigram` 支持子串检索，但不足三个 Unicode 字符的全文查询不匹配。推断：例如二字词“芯片”不能靠整体切换 trigram 解决。可比较保留词项索引并增加短词回退、trigram 子串索引、应用层分词三个方案；先用真实查询集决定，不先引入外部搜索服务。[SQLite FTS5：tokenizer 与 trigram 限制](https://www.sqlite.org/fts5.html#tokenizers)
4. **成熟阅读器的价值集中在整理与继续阅读。** FreshRSS 官方文档覆盖分类、过滤搜索、收藏、移动端、OPML 和快捷键；Miniflux 强调未读扫描与正文阅读。这些是功能事实，不是用户偏好调查。对本项目的推断是完善已存在的阅读动作和数据完整性，比重做页面或复制所有功能更适合个人自用。[FreshRSS 功能](https://freshrss.github.io/FreshRSS/en/)、[FreshRSS 配置与快捷键](https://freshrss.github.io/FreshRSS/en/users/05_Configuration.html)、[Miniflux 产品说明](https://miniflux.app/)
5. **本地推理仍需要资源预算。** Ollama 文档说明并发上下文会增加内存需求，队列过载可能返回 503，`keep_alive` 可控制模型驻留。生成接口返回总耗时、加载耗时和 token 计数；结构化输出可通过 JSON schema 限定形状。推断：先记录这些指标并限制项目侧并发，再调模型和上下文。JSON 格式校验不能证明摘要事实正确。[Ollama FAQ](https://docs.ollama.com/faq)、[Generate API](https://docs.ollama.com/api/generate)、[Structured Outputs](https://docs.ollama.com/capabilities/structured-outputs)

## 三个方向比较

下面是基于用户目标和代码差距的工程判断，不是市场评分。

| 方向 | 直接收益 | 主要成本与风险 | 优先级与边界 |
| --- | --- | --- | --- |
| A. 可靠、节制的抓取与交付 | 减少重复正文下载、重复任务和故障时的人工处理；可解释“源没更新”还是“源坏了” | HTTP 响应抽象、缓存验证、调度状态需要一起定义；部分源不支持验证器 | **P0，先做**。从一个 `/rss` 挂载纵向落地；不用外部队列、分布式调度 |
| B. 个人连续阅读与检索 | 跨天继续未读；中文关键词找回旧文章；减少重复浏览 | 分页与批量已读语义要一致；中文召回与索引大小存在取舍 | **P1**。复用现有 UI、FTS5、已读表；先把待处理队列做完整 |
| C. 可评估、可恢复的本地 AI | 机器重启后能继续；摘要更可信；避免后台任务挤占手动请求 | 状态迁移、模型与提示词版本、质量样本维护；性能受硬件影响 | **P1，在抓取稳定后**。优先摘要任务管理；语义推荐、向量数据库和跨文章自动综合延后 |

推荐顺序 A → B → C。若真实日志显示 AI 排队或内存已影响日常使用，把 C 的“并发上限与任务去重”提前并入 A，其余质量功能仍按阶段推进。

## 阶段一：一个 RSS 源可以长期可靠刷新

**实施状态：核心流程已落地。** 通用 RSS 保存正文与验证器，支持 304、两种 Retry-After、持久退避、按主机限制并发及换源隔离；阅读请求与调度共享正在执行的抓取，健康页展示检查状态。持久化失败在抓取日志中单独标记。新增表在首次启动时创建，既有条目无需迁移。定量运维部分仍待实际运行：当前记录的是解码后 UTF-8 正文字节数和刷新总耗时，没有独立排队时间序列、线上流量统计或七天样本；不能据此宣称已测得带宽/性能收益。下一开发阶段仍是连续阅读与中文检索。

**可交付切片：** 在 `/index` 挂载一个原生 RSS → 按计划条件抓取 → 未变化时复用数据 → 故障退避 → 管理页显示上次成功检查、上次内容变化、下次尝试及失败原因 → 阅读器继续展示已存内容。该顺序覆盖配置、HTTP、存储、调度和可见结果。[现有链路](../../CONTEXT.md)

建议实现：

- 在共享 HTTP 层增加小型响应模型，保留现有正文调用的兼容入口；条件缓存先只用于公开、无额外身份请求头的通用 RSS。验证器必须与可复用的响应正文或对应的 feed 快照一起保存；只有验证器、没有数据时，重新做无条件请求。持久数据访问仍统一经过 `FeedStore`。
- 通过同路由只允许一个运行任务、每主机并发上限、有上限的失败退避处理突发。支持两种 `Retry-After` 表达；过长等待保存为下次可执行时间，不占用线程睡眠。手动刷新也遵守并发限制。
- 将“检查成功”“数据改变”“持久化失败”“上游失败”分开记录。`304` 增加检查次数，不增加新条目数；首次发现时间保持稳定。对带 Cookie、Authorization、Vary 的来源另行设计缓存隔离，首版不泛化为透明 HTTP 代理。[HTTP 缓存规则](https://www.rfc-editor.org/rfc/rfc9111.html#section-4)
- 记录每路由请求次数、响应状态、正文传输字节、新条目数、总耗时与排队时间；先保留固定周期，拿到至少七天历史后再评估按来源更新频率调节周期。[调度实践参考](https://miniflux.app/docs/configuration.html)

**验收目标：**

| 场景 | 可判定结果 |
| --- | --- |
| 测试源依次返回 `200 + ETag`、`304`、更新后的 `200` | 第二次发送正确验证器、条目不丢失、首次发现时间不变；第三次仅新增真实新条目 |
| 同一路由的定时与手动抓取同时到达 | 同一时刻上游活动抓取数不超过 1；完成后可以再次触发 |
| 测试源返回 429/503 与两种格式的 `Retry-After` | 指定时间前不再次请求；恢复后能按计划继续，失败状态可见 |
| 一个慢源与一个正常源并存，期间 Ollama 不可用 | 正常源仍能按计划持久化；阅读器可读；AI 故障不改变抓取结果 |
| 重启与恢复 | 已存条目、验证器及恢复时间一致；没有对应正文时不会错误复用 304 |

上线观察只报告实测的 304 比例、每次检查正文传输量、成功检查间隔 P95 和失败恢复时间。对不支持验证器的源，304 比例为零完全合理。不得预先宣称“节省 80% 流量”。

## 阶段二：未读内容跨天可续读，中文文章可找回

**2026-10-04 实施进展：** 新增 `/reader/unread`，跨时间窗口访问所有保留的未读文章；每页 50 条，使用入库 ID 游标。来源、收藏与标题/正文描述/摘要的中文关键词筛选在数据库中完成，批量已读仅影响当前页。沿用全局 URL 身份与首次来源归属，复用卡片、快捷键和摘要展示。1,200 条连续翻页与并发新增、重启持久化已有自动化用例；浏览器使用 160 条隔离数据验证翻页、筛选、计数与失败恢复。此切片尚不包含分类映射、FTS 中文排序改造、30 条人工查询集、恢复演练或 10 万条性能验证。

**后续切片（2026-10-05 完成）：** 历史搜索补齐中文短词、多个关键词跨标题/描述/摘要共同匹配、字面符号搜索，以及安全的命中摘录。沿用英文 FTS 整词语义，中文与符号用字面条件筛选；没有更换分词器。30 条开发者合成回归场景通过，它们不是用户人工标注的相关性评估。最终 `FeedStore.searchHits` 在 10 万条短合成文章上的预热查询中位数为中文约 146–171ms、英文约 0.96ms、中英混合约 1.07ms；没有 HTTP、冷缓存或并发负载指标，不能据此声称达到生产 P95 目标。见[搜索实施记录](../plans/2026-10-04-chinese-search.md)。索引增量初始化与原子写入已在同日后续切片完成。后续仍需处理真实查询集、长文章与并发负载、备份恢复及分类映射。

**可交付切片：** 文章入库 → 进入持久未读列表 → 按分类或关键词定位 → 读完并保存状态 → 次日从剩余内容继续。沿用已有分类、收藏、快捷键与简报，只补齐查询和动作语义。[已有阅读入口](../../src/main/java/app/ReaderResource.java)

建议实现：

- 未读、分类与收藏筛选移到 `FeedStore` 查询层；使用稳定排序及游标加载后续内容。批量已读默认只作用于用户明确选中的范围；全结果操作需要展示范围，避免把尚未看见的内容误标为已读。
- 确定 URL 在“同一文章出现在多个路由”时的阅读身份：建议已读和收藏继续按文章 URL 共享，列表合并文章并保留来源信息；这是产品选择，实施时补用例。
- 建立 30 条人工确认的中英文查询集，包含二字词、三字以上子串、英文、标点、摘要独有词、跨来源重复 URL。先验证现有 FTS，再比较短词回退与 trigram；仅在结果支持时加入分词依赖。索引重建作为版本迁移或修复操作，常规启动与写入尽量增量维护。[FTS5 官方文档](https://www.sqlite.org/fts5.html)
- 在数据保留和导入能力扩展前建立恢复演练：数据库使用一致性备份方式，配置文件单独保存，再在临时目录恢复阅读状态。SQLite 官方在线备份 API 可生成一致快照；具体 Java 调用需核对项目 JDBC 驱动支持情况。[SQLite Backup API](https://www.sqlite.org/backup.html)

**验收目标：**

| 场景 | 可判定结果 |
| --- | --- |
| 准备 1,200 条跨三天记录，夹杂已读、收藏和重复来源 | 全部唯一未读文章可逐页访问，无遗漏或重复；总数与数据库按选定身份去重后的结果一致 |
| 连续翻页同时有新文章入库 | 不因偏移漂移重复读到或跳过已有条目 |
| 30 条人工查询样本 | 预先标注的目标文章至少 27 条进入前 10；二字词和摘要词单独报告结果，不能被英文平均分掩盖 |
| 操作后刷新页面、重启服务，再做恢复演练 | 已读、收藏与筛选结果一致；批量已读范围符合界面说明 |
| 固定机器、固定 10 万条测试数据 | 记录查询与页面响应 P50/P95、数据库和索引大小；建议普通查询 P95 目标 ≤300ms，达不到时据实定位，不视为已验证能力 |

OPML 导入导出是随后可独立交付的小切片：只映射标准 RSS 订阅，预览去重后再保存。自定义路由、凭据和调度字段另用项目配置备份承载，避免伪装成通用 OPML 能力。[FreshRSS 导入实践](https://freshrss.github.io/FreshRSS/en/users/02_First_steps.html)

## 阶段三：本地摘要可排队、可恢复、可评估

2026-10-05 状态：首个可恢复队列切片已落地。当前保留已有 `queued/running/success/error` 状态，固定一个活动推理任务；失败仅显式重试，排队暂停/恢复，不增加租约或自动重试。下方资源指标、缓存版本、质量样本与并发配置为后续目标。

**可交付切片：** 文章入库或手动请求摘要 → 一个持久任务 → 有限并发执行 → 展示排队/运行/成功/失败状态 → 重启后恢复 → 生成结果能追溯到输入与模型。摘要仍是可选增强，原文始终可读。[已有摘要状态](../../src/main/java/app/store/SummaryStatus.java)

建议实现：

- 先复用数据库中的原始描述与已缓存正文，让手动和定时摘要使用同一输入解析流程；文章 HTTP 抓取经过共享 `FetchClient`。比较纯 DOM 清理后单次摘要与当前模型抽取后再摘要的质量；只有前者在固定样本上不退化，才取消普遍的抽取推理。对旧 `ai_extracts` 标明来源类型或版本，避免把模型改写文本当成原始证据。[当前抽取链路](../../src/main/java/app/ai/ArticleExtractor.java)、[当前摘要链路](../../src/main/java/app/ai/ArticleSummarizer.java)
- 从应用级 AI 并发 1 起步，按实测硬件能力调整。手动请求和后台请求合并到同一个按文章去重的任务入口；手动请求优先，后台新增条目其次；没有正文的任务明确失败或跳过，禁止无限重试。
- 扩展已有运行记录为 `queued/running/succeeded/failed`，保存尝试次数、下次重试时间及任务租约；重启时回收过期任务。用 SQLite 完成，保持项目“不引入外部队列”的边界。[项目边界](../../CONTEXT.md)
- 摘要版本标识包含正文指纹、模型标识和提示词版本。模型配置变化先只影响新任务；已有摘要显式触发重生成，避免一次切换耗尽机器资源。
- 记录 Ollama 加载、输入处理、输出处理耗时与 token 数；同时记录项目侧排队时间。依据冷启动比例选择 `keep_alive`，不默认永久驻留。保留原文链接与输入截断状态；结构化输出只在确实需要字段时引入，不能代替人工质量评估。[Ollama API](https://docs.ollama.com/api/generate)、[Ollama 资源管理](https://docs.ollama.com/faq)、[结构化输出](https://docs.ollama.com/capabilities/structured-outputs)
- 用 30 篇固定文章建立质量样本：中文新闻、英文技术文、长文、缺正文、含数字和引述的文章各占一定比例。提示词要求仅依据文章内容、保留不确定语气；对不足输入显式返回“内容不足”，不要补事实。以人工回溯原文为准，不只让另一个模型打分。

**验收目标：**

| 场景 | 可判定结果 |
| --- | --- |
| 相同文章同时被定时任务与手动操作请求 | 同一摘要版本只调用一次生成；两个入口看到同一状态 |
| 执行到一半重启、Ollama 返回 503 或超时 | 任务能在有限重试内恢复或进入明确失败；没有永久 running；已完成结果不重复计算 |
| 提交 100 个任务并同时抓取新内容 | 活动推理数不超过设置上限；读取页面和新文章持久化不等待摘要全部完成 |
| 30 篇人工评估 | 样本中不存在新增且无法由输入支持的人名、数字或结论；至少 27 篇覆盖人工标注的主要事实；内容不足样本不捏造。此结果只说明样本表现，不承诺任意文章零错误 |
| 性能记录 | 分别给出冷/热启动生成 P50/P95、排队 P95、失败率与峰值内存；实测前不承诺“几秒一篇” |

## 已有 ADR 的优先级与后续触发条件

通用 CSS 选择器路由维持 **accepted、implementation deferred**，排为 **P2**。这没有推翻“降低加源门槛”的决策，而是根据本次明确的个人自用目标调整实施顺序。[ADR 0001](../adr/0001-generic-scrape-route-for-new-sources.md)

建议启动条件：可靠抓取已通过阶段一验收，并且出现至少两个实际想订阅、无稳定 RSS/API、可由静态 HTML 选择器覆盖的来源。此时交付“填 URL 与选择器 → 预览真实条目 → 校验唯一链接和日期 → 保存挂载 → 加入既有调度”的小闭环。首版不引入 JavaScript 执行、登录态自动化、动态插件或 DSL；范围沿用 ADR。FreshRSS 的抓取功能和 Miniflux 的 CSS 正文规则可作为交互参考，但不能据此假定任意站点都能被选择器稳定抓取。[FreshRSS 用户手册](https://freshrss.github.io/FreshRSS/en/users/02_First_steps.html)、[Miniflux 抓取规则入口](https://miniflux.app/docs/ui.html)

暂缓的方向包括：向量数据库、自动兴趣推荐、跨文章综合推理、多用户、原生移动端、浏览器抓取引擎及大规模扩充内置路由。触发这些方向应有具体使用证据，例如关键词检索反复无法找回内容、确有跨设备 API 客户端需求，或静态抓取不能满足已确认来源；不能仅因技术可用而加入。

## 交付时的测量约定

- 先记录七天实际抓取与使用情况：配置的来源数、每天新增唯一文章、失败来源、未读积压、实际搜索词和手动摘要请求。仅在本地记录，不发送遥测。
- 每个阶段单独交付、单独验收。以固定 fixture 验证正确性，以固定机器和固定数据集对比性能；记录版本、数据量、配置和测试日期，避免把上游网站变化误当优化结果。
- 决策复核依据是“每天减少了多少无效操作、漏读、重复请求与故障处理”，不是类数量、路由数量或 AI 调用量。本文的顺序和目标是建议，尚无运行数据证明收益。
